Docs / BullMQ / The BullMQ module

Full BullMQ, typed

The same typed job map and kernel module as @rhythmjs/queue, on full BullMQ: stalled-job recovery, Redis-durable work, and every BullMQ option passed through untouched.

Install the package #

@rhythmjs/bullmq is BullMQ-backed job queues for Rhythm: the same typed job map and kernel-module discipline as @rhythmjs/queue, on full BullMQ. It requires Redis and brings BullMQ's ioredis dependency with it.

Why BullMQ instead of @rhythmjs/queue #

Choose this package for BullMQ's production machinery: Redis-durable jobs, stalled-job recovery with lock renewal (a job whose worker dies is picked up again), Lua-scripted atomic state transitions, replica-coordinated Job Schedulers, per-job history and retention options, and the Bull Board / Taskforce ecosystem. Choose @rhythmjs/queue when you want zero queue dependencies on Bun natives.

The two packages provide the same queueService context key with the same method surface, so switching is a one-line change at the registration site; handlers and producers do not move. The honest differences: here job ids are string | undefined (BullMQ's own typing), and job options are BullMQ's JobsOptions passed through untouched.

The kernel module #

Options: name (queue name, default rhythm), connection (ioredis ConnectionOptions — an options object or an existing instance; default 127.0.0.1:6379), prefix (Redis key prefix), and defaultJobOptions (BullMQ defaults for every job). The module owns the BullMQ lifecycle: on the kernel's teardown() every worker closes first, then the queue, in reverse provider order.

Produce and process #

Job options are BullMQ's own JobsOptions, passed through untouched — delay, attempts, backoff, priority, removeOnComplete/removeOnFail, jobId, lifo, deduplication, and everything else BullMQ accepts. Each process() call creates one BullMQ Worker on the queue, dispatching to processors by name with a typed payload and JobInfo ({ id, name, attemptsMade }; the id can be undefined).

A job with no registered processor throws no processor registered for job "…" and lands in BullMQ's retry/failed flow like any other failure. onCompleted and onFailed wrap the worker's own completed/failed events; a failed event that arrives without a job reports the name as "unknown". counts() forwards getJobCounts() — waiting, active, delayed, completed, failed, and the rest of BullMQ's states.
