Docs / BullMQ / Schedulers & queue access

Repeats, and the whole Queue

Replica-coordinated Job Schedulers keyed by job name, BullMQ's own RepeatOptions untouched, and direct access to the underlying Queue for pausing, inspection, flows, and dashboards.

Job Schedulers #

schedule(name, repeat, payload, options?) upserts a BullMQ Job Scheduler keyed by the job name, with { name, data, opts } as the template for every job it spawns. Schedulers are Redis-coordinated: register the same schedule from every replica and it still fires once; the natural pattern is to declare schedules at boot on all instances.

repeat is BullMQ's own RepeatOptions passed through untouched - pattern (BullMQ's cron dialect), every, tz, limit, startDate/endDate, and the rest. Note the field is tz here, where @rhythmjs/queue spells it timezone, the one naming difference between the two packages' repeat options.

Unschedule #

unschedule(name) removes the Job Scheduler via removeJobScheduler. Jobs it already enqueued are unaffected; only future firings stop.

The escape hatch: queueService.queue #

queueService.queue is the underlying BullMQ Queue instance: everything the typed facade does not wrap is one property away, with no second connection:

The same instance is what UI tooling wants: hand it to Bull Board's BullMQAdapter or Taskforce and the dashboard sees the queue exactly as your app does. For parent-child flows, construct BullMQ's FlowProducer alongside with the same connection options, so flow jobs land on this queue and your named processors handle them like any other job.

Testing the wiring #

The package's own suite is the pattern to copy. Facade wiring is tested with mock.module("bullmq", …) from bun:test, substituting recording Queue/Worker fakes; no Redis server needed. Live behavior (retries, schedulers, real dispatch) runs in a separate suite gated on an environment variable, so CI without Redis skips it cleanly.
