## Feature modules

As features multiply, each one becomes its own module: a `Rhythm` instance with `{ type: "module", name }` that owns its startup values and controllers. The notes feature now ships as one unit:

```ts
// src/notes/notes.module.ts
export const notesModule = new Rhythm<RhythmHttpContext, { notesService: NotesService }>({
  name: "notes",
  type: "module",
});

notesModule.context.notesService = createNotesService();

notesModule.use(notesController.middleware());
```

## Register and export

`register(module, exportValue?)` mounts another module inside this one. The child runs on a copy of the parent's context with its own `context` merged on top, so it inherits everything the parent holds, its middleware runs in place, and what it adds stays *encapsulated*: nothing leaks to the parent unless `exportValue` picks it out. Registration also type-checks that the parent satisfies the child's input. Explicit boundaries, not folder conventions:

```ts
export const appModule = new Rhythm<RhythmHttpContext>({ name: "app", type: "module" })
  .register(notesModule, ({ notesService }) => ({ notesService })) // export the service
  .register(auditModule)                                          // keep everything private
  .use((ctx) => {
    // ctx.notesService is available and typed here; auditModule&#x27;s internals are not
  });
```

Because services are built eagerly, a module that cannot construct its service throws while the app is being assembled — at startup, with the original error — never on the first request.

## The forRoot pattern

Reusable modules follow one naming convention: a `somethingModule.forRoot(options)` factory returning a configured `Rhythm` module. Every @rhythmjs package that exposes a service ships one, and your own shared modules should too:

```ts
export const cacheModule = {
  forRoot(options: { ttl?: number } = {}) {
    const module = new Rhythm<{}, { cacheService: CacheService }>({ type: "module", name: "cache" });
    module.context.cacheService = createCacheService(options);
    return module;
  },
};

appModule.register(cacheModule.forRoot({ ttl: 300 }), (v) => v);
```

## The app as a tree

The finished shape is a tree of modules with the app module at the root — startup values flow down to children, exports flow back up only where you choose, and every request runs the flattened onion top to bottom:

```text
appModule
├─ configModule.forRoot(...)     // step 7
├─ notesModule                   // service + controller
├─ mailerModule.forRoot(...)     // your own — next step
├─ eventsModule.forRoot(...)     // step 11
└─ 404 tail
```

Read [Encapsulated modules](/rhythm/modules/) for the full semantics — what is hidden, what `exportValue` sees, and how module errors propagate. The next step turns this pattern around: instead of consuming ready-made modules, you author your own.
