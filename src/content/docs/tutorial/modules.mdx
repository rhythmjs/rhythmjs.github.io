## Feature modules

As features multiply, each one becomes its own module: a `Rhythm` instance with a `name` that owns its startup values. A module is the same kind of object as the app, just smaller. The notes feature now ships its service as one unit:

```ts
// src/notes/notes.module.ts
import { Rhythm, decorate } from "@rhythmjs/rhythm";
import { createNotesService } from "./notes.service";

export const notesModule = new Rhythm({ name: "notes" }).register(
  decorate(() => ({ notesService: createNotesService() })),
);
```

## Include and export

`include(module, pick?)` runs a module once, at startup, and pulls the fields `pick` returns into the parent's startup context. Everything the module builds stays *encapsulated*: nothing leaks to the parent unless `pick` selects it. Registering also type-checks that the parent satisfies the child's input, and the module's own cleanups are registered with the parent, so `app.stop()` closes the whole tree. Explicit boundaries, not folder conventions:

```ts
// src/app.module.ts
export const appModule = new Rhythm({ name: "app" })
  .register(decorate(() => ({ appService })))
  .register(include(notesModule, ({ notesService }) => ({ notesService }))) // export the service
  .register(include(auditModule))                                          // keep everything private
  .use(mount(appController))
  .use(mount(notesController)); // ctx.notesService is typed here; auditModule's internals are not
```

Because modules run eagerly, one that cannot construct its service throws while the app is being assembled — at startup, wrapped as `included module "notes" failed` with the original error as `cause` — never on the first request.

## Include or mount

Two functions compose pipelines, and the difference is *when* they run:

- `include(module, pick?)` is **startup time**. The module runs once with the app's startup context and contributes startup values. Use it for providers: services, config, pools.
- `mount(plugin)` is **request time**. The plugin runs on every request and whatever it derives stays sealed inside it. Use it for routers, and for modules that ship routes (the next step builds one).

## The forRoot pattern

Reusable modules follow one naming convention: a `somethingModule.forRoot(options)` factory returning a configured `Rhythm` module. Every @rhythmjs package that exposes a service ships one, and your own shared modules should too. Here the module takes its dependencies as options instead of building them out of thin air:

```ts
export const cacheModule = {
  forRoot(options: { ttl?: number } = {}) {
    return new Rhythm({ name: "cache" }).register(decorate(() => ({ cacheService: createCacheService(options) })));
  },
};

appModule.register(include(cacheModule.forRoot({ ttl: 300 }), ({ cacheService }) => ({ cacheService })));
```

## The app as a tree

The finished shape is a tree of modules with the app at the root — startup values flow in where you `include` them, exports flow only where you pick, and every request runs the flattened onion top to bottom:

```text
appModule
├─ configModule.forRoot(...)     // step 7
├─ notesModule                   // service (step 8: forRoot(db))
├─ mailerModule.forRoot(...)     // your own — next step
├─ openapiModule / scalarModule  // step 12
└─ notesController, health, ...  // mounted routers
```

Read [Encapsulated modules](/rhythm/modules/) for the full semantics — what is hidden, what `pick` sees, and how module errors propagate. The next step turns this pattern around: instead of consuming ready-made modules, you author your own.
