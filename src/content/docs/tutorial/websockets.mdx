## A chat route

`@rhythmjs/ws` routes WebSocket upgrades onto Bun's own model: handlers are Bun `WebSocketHandler` members, fan-out is native pub/sub, and each route decides its connection's typed `ws.data`. Like the controllers, a `RhythmWs` is a pipeline you mount into the app. Start with a chat where one socket joins whichever room the client asks for:

```bash
bun add @rhythmjs/ws
```

```ts
// src/chat/chat.ws.ts
import { RhythmWs } from "@rhythmjs/ws";

type Command = { type: "join"; room: string } | { type: "say"; text: string };

export const chatWs = new RhythmWs().ws("/ws", {
  upgrade() {
    return { handle: crypto.randomUUID().slice(0, 6), room: undefined as string | undefined };
  },
  message(peer, message) {
    const command = JSON.parse(String(message)) as Command;

    if (command.type === "join") {
      if (peer.data.room) peer.unsubscribe(`room:${peer.data.room}`);
      peer.data.room = command.room;
      peer.subscribe(`room:${command.room}`);
      peer.publish(`room:${command.room}`, `${peer.data.handle} joined`);
      return;
    }

    if (peer.data.room) peer.publish(`room:${peer.data.room}`, `${peer.data.handle}: ${command.text}`);
  },
  close(peer) {
    if (peer.data.room) peer.publish(`room:${peer.data.room}`, `${peer.data.handle} left`);
  },
});
```

`upgrade()` runs once per handshake and returns the connection's `ws.data`; its type flows into every handler, so `peer.data.handle` is a `string` and `peer.data.room` is `string | undefined`. `ws.data` is a plain object per connection, which is why the current room can live on it. Rooms themselves are just topic names: no room registry to maintain.

## Mount and serve it

The socket joins the app beside the controller, and `main.ts` hands Bun the shared `websocket` handler. `toFetchHandler` passes Bun's server through as `ctx.server`, which is what performs the upgrade:

```ts
// src/app.module.ts
import { Rhythm, mount } from "@rhythmjs/rhythm";
import { chatWs } from "./chat/chat.ws";

export const appModule = new Rhythm()
  /* ...services, middleware... */
  .use(mount(notesController))
  .use(mount(chatWs));
```

```ts
// src/main.ts
import { createWebsocket } from "@rhythmjs/ws";

const server = Bun.serve({
  port,
  fetch: toFetchHandler(appModule),
  websocket: createWebsocket({ idleTimeout: 120, maxPayloadLength: 16 * 1024 }),
});
```

Only `GET` requests with an `Upgrade: websocket` header whose path matches `/ws` are touched; everything else flows on to the controllers as before. A browser client is a plain `WebSocket` and one message:

```ts
const socket = new WebSocket("ws://localhost:3000/ws");
socket.onopen = () => socket.send(JSON.stringify({ type: "join", room: "general" }));
socket.onmessage = (event) => console.log(event.data);
```

## Authenticate the handshake

A socket is long-lived, so decide who is on it once, at the handshake, and keep the answer in `ws.data`. `use()` is the router's middleware, run before `upgrade`, and the session from the security chapter is already on the HTTP request that opens the socket, since browsers send cookies with the handshake:

```ts
import { session } from "@rhythmjs/http/session";

export const chatWs = new RhythmWs().use(session()).ws("/ws", {
  upgrade(ctx) {
    const userId = ctx.session.get<string>("userId");
    if (!userId) return ctx.error(401);        // refuses the handshake
    return { userId, room: undefined as string | undefined };
  },
  message(peer, message) {
    /* peer.data.userId replaces the random handle */
  },
});
```

Writing a response (`ctx.error(401)`) refuses the upgrade; nothing opens. Authorization is the same idea one level down: the `join` branch is where you check that `peer.data.userId` may enter the requested room before you subscribe.

<Callout title="Cross-site hijacking is closed by default">

Browsers attach cookies to WebSocket handshakes and are exempt from CORS. `RhythmWs` therefore answers `403` to any handshake whose `Origin` does not match the request's own host. If your frontend lives on another origin, pass `new RhythmWs({ origin: ["https://app.example.com"] })`.

</Callout>

## Push from the controllers

Anything with Bun's server can publish to a topic, sockets or not. In an HTTP handler that is `ctx.server`, so the notes controller can announce a new note into a room:

```ts
// in the notes controller
.post("/", requireAuthentication(), validate("body", createNoteSchema), (ctx) => {
  const note = ctx.notesService.create(ctx.valid.body);
  ctx.server?.publish("room:general", JSON.stringify({ type: "note.created", note }));
  ctx.json(note, 201);
})
```

Bun's pub/sub is in-process; running several replicas needs a backplane, as the [ws docs](/ws/serving/) explain. The package pages also cover [typed `ws.data`](/ws/routes/), [middleware and auth](/ws/middleware/), and testing with [`@rhythmjs/testing/ws`](/testing/ws/).
