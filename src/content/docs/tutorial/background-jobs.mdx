## Register jobs

Work that happens on a clock, not a request, is a job. `@rhythmjs/cron` is a thin pipeline over Bun's own `Bun.cron`: jobs are named, handlers are ordinary `(ctx, next)` functions like route handlers, and there is no scheduler of our own. Like the controllers and the socket, a `RhythmCron` carries a context type for what its handlers use:

```bash
bun add @rhythmjs/cron
```

```ts
// src/notes/notes.cron.ts
import { RhythmCron } from "@rhythmjs/cron";
import type { NotesService } from "./notes.service";

export const notesCron = new RhythmCron<{ notesService: NotesService }>({ tz: "UTC" })
  .cron("prune-empty", "*/30 * * * *", (ctx) => {
    for (const note of ctx.notesService.list()) {
      if (!note.content) ctx.notesService.remove(note.id);
    }
  })
  .cron("digest", { schedule: "0 9 * * MON-FRI", tz: "America/New_York" }, (ctx) => {
    console.log(`digest at ${ctx.job.firedAt.toISOString()}: ${ctx.notesService.list().length} notes`);
  });
```

A schedule is a five-field cron expression, a nickname such as `"@hourly"`, or `{ schedule, tz }` to override the instance's time zone for one job. Expressions and time zones are validated when you register the job, a duplicate name throws, and so does a schedule that can never fire, so a typo fails at startup rather than silently never running. Every handler also gets `ctx.job`: `name`, `schedule`, `tz`, and `firedAt`.

## Start it with the app

Jobs get the app's startup context, the same one the services come from, and stop with it. Register `startCron(notesCron)` on the app and `app.stop()` takes care of the rest:

```ts
// src/app.module.ts
import { Rhythm, decorate, mount } from "@rhythmjs/rhythm";
import { startCron } from "@rhythmjs/cron";
import { createNotesService } from "./notes/notes.service";
import { notesCron } from "./notes/notes.cron";

export const appModule = new Rhythm()
  .register(decorate(() => ({ notesService: createNotesService() })))
  .register(startCron(notesCron))      // starts the timers; stops them on appModule.stop()
  .use(mount(notesController));
```

`startCron` is a startup-time register callback, not request middleware: the jobs begin when the app does, with the context your `decorate` and `include` calls built. Without the app, `notesCron.start(input)` and `notesCron.stop()` do the same by hand, and `notesCron.running` tells you which state you are in.

## Wrap every run

`use()` is middleware around *every* job, which is where cross-cutting concerns live: timing, logging, a lock. Each run is a fresh pass through the chain, so a job can be as small as its body:

```ts
export const notesCron = new RhythmCron<{ notesService: NotesService }>({ tz: "UTC" })
  .use(async (ctx, next) => {
    const started = performance.now();
    console.log(`[cron] ${ctx.job.name} started`);
    await next();
    console.log(`[cron] ${ctx.job.name} finished in ${Math.round(performance.now() - started)}ms`);
  })
  .cron("prune-empty", "*/30 * * * *", (ctx) => {
    for (const note of ctx.notesService.list()) {
      if (!note.content) ctx.notesService.remove(note.id);
    }
  });
```

Extension middleware (`derive(...)`) works as on a router, widening what later middleware and the job handlers see. Handlers may also be a chain: `.cron(name, schedule, guard, handler)`.

## A manual trigger

For an admin who needs the digest now, or a test that must not wait for the clock, `cron.run(name, input)` runs a job immediately through the same middleware chain and resolves when it finishes. Unlike a scheduled run, an error here rejects, so the HTTP route reports it:

```ts
// in the notes controller
.post("/api/jobs/:name/run", requireAuthentication(), requireRoles(["admin"]), async (ctx) => {
  if (!notesCron.jobs.some((job) => job.name === ctx.params.name)) return ctx.error(404, "No such job");
  await notesCron.run(ctx.params.name, { notesService: ctx.notesService });
  ctx.json({ ok: true });
})
.get("/api/jobs", requireAuthentication(), (ctx) => {
  ctx.json(notesCron.jobs.map((job) => ({ ...job, next: notesCron.next(job.name) })));
})
```

`cron.jobs` lists name, schedule and time zone, and `cron.next(name)` previews the next fire time, a `Date` or `null`. `run` throws a `RangeError` for an unknown name, hence the explicit 404 above.

## Time zones

Without a `tz`, a job runs in the process's local time zone, which differs between your laptop and a server. Set `tz` on the instance for a default (the `"UTC"` above), and on a single job with the object form when it follows someone's wall clock, as the 9 o'clock digest above follows New York. Bun resolves daylight-saving changes for named zones; `cron.next(name)` is the quick way to check what a job will actually do.

## Errors and onError

A job that throws does not stop the schedule: the error goes to `onError(error, ctx)` (by default `console.error`), and the job fires again at its next time. Handle failures where you already handle them: the logger, your error tracker.

```ts
export const notesCron = new RhythmCron<{ notesService: NotesService }>({
  tz: "UTC",
  onError(error, ctx) {
    console.error(`job ${ctx.job.name} failed at ${ctx.job.firedAt.toISOString()}`, error);
  },
});
```

Runs never overlap: Bun schedules the next fire only after the current run settles, so a slow `prune-empty` skips ticks rather than piling up.

## Stop cleanly

Because `startCron` registered a cleanup, stopping the app stops the timers. In the graceful shutdown from the observability chapter, that is one line in the `close` hook:

```ts
const server = Bun.serve({ port, fetch: toFetchHandler(appModule) });

process.on("SIGTERM", async () => {
  await appModule.stop();   // stops the cron timers and every other cleanup
  server.stop();
});
```

<Callout title="Scheduling lives in your process">

Cron here is in-process. Nothing is persisted: runs missed while the app was down are not replayed, and with several replicas every one of them fires every job. If a job must run on one instance only, take a lock in `use()` (a Redis `SET NX`, a database advisory lock) and call `next()` only when you hold it. See the [cron docs](/cron/) for the full lifecycle and API.

</Callout>
