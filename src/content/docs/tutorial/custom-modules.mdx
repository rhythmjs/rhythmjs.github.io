## A module of your own

Every @rhythmjs module — config, health, OpenAPI — is built from the same three pieces you already know: an options interface, a service factory, and a `forRoot` factory that builds the service and adds it to a `Rhythm` module's startup context. Nothing is reserved for the framework; a mailer module of your own is the identical shape, an infrastructure module in the sense of the previous step:

```ts
// src/mailer/mailer.module.ts
import { Rhythm, decorate } from "@rhythmjs/rhythm";

export interface MailerOptions {
  from: string;
  transport?: "smtp" | "console";
}

export function createMailerService(options: MailerOptions) {
  const transport = options.transport ?? "console";
  return {
    async send(to: string, subject: string, body: string): Promise<void> {
      if (transport === "console") console.log(`[mail] ${options.from} -> ${to}: ${subject}`);
      else await smtpSend({ from: options.from, to, subject, body }); // your SMTP client
    },
    close(): Promise<void> {
      return transport === "smtp" ? smtpClose() : Promise.resolve();
    },
  };
}

export type MailerService = ReturnType<typeof createMailerService>;

export const mailerModule = {
  forRoot(options: MailerOptions) {
    const mailerService = createMailerService(options);
    return new Rhythm({ name: "mailer" }).register(
      decorate(() => ({ mailerService })),
      () => mailerService.close(), // runs when the app that included the module stops
    );
  },
};
```

The module owns its shutdown: the cleanup passed to `register` runs on `stop()`, and `include()` registers the module's `stop()` as a cleanup of the parent, so one `appModule.stop()` closes everything. If building the service is async (connecting, loading), make `forRoot` async and `await` it where you include it — `await configModule.forRoot(...)` works exactly this way.

Because `forRoot` builds a fresh service every call, create the configured instance once, export it, and let everyone include *that* instance — the feature that sends mail, and the app for lifecycle:

```ts
// src/mailer/mailer.module.ts, below mailerModule
export const appMailerModule = mailerModule.forRoot({ from: "notes@example.com" });
```

```ts
// src/invites/invites.module.ts, a feature that sends mail
export const invitesModule = new Rhythm({ name: "invites" })
  .register(include(appMailerModule, ({ mailerService }) => ({ mailerService })))
  .register(decorate(({ mailerService }) => ({ invitesService: createInvitesService(mailerService) })))
  .use(mount(invitesController));

// src/app.module.ts: a mounted module registers no cleanups, so the app includes it for lifecycle too
appModule.register(include(appMailerModule)).use(mount(invitesModule));
```

The mailer is an implementation detail of the invites service; the controller never sees it.

## Reusable feature modules

The feature modules of the previous step are specific to this app. The same shape works for a reusable one: a `forRoot(options)` that returns a module which builds its service from the options and mounts its own router. The parent mounts it as one line. Because `mount()` runs it per request and seals what it derives, only its routes are observable:

```ts
// src/admin/admin.module.ts
import { Rhythm, decorate, mount } from "@rhythmjs/rhythm";
import { RhythmRouter } from "@rhythmjs/router";
import { authenticate } from "../auth/authenticate";
import { requireRole, requireUser } from "../auth/guards";

const adminController = new RhythmRouter<{ adminService: AdminService }>({ name: "admin" })
  .use(authenticate)
  .use(requireUser)
  .get("/admin/stats", requireRole("admin"), (ctx) => {
    ctx.json(ctx.adminService.stats());
  });

export const adminModule = {
  forRoot(options: AdminOptions) {
    return new Rhythm({ name: "admin" })
      .register(decorate(() => ({ adminService: createAdminService(options) })))
      .use(mount(adminController));
  },
};

// the parent sees routes, not services:
appModule.use(mount(adminModule.forRoot({ retainDays: 30 })));
```

This is how `healthRoutes` and the OpenAPI docs module work under the hood: functionality arrives as a mountable unit, and the boundary is the module, not a folder convention. Remember the rule from the previous step: it is mounted, never included, and if it opens resources of its own, whoever hosts it includes them for lifecycle. The `authenticate` step and the guards used above are the ones from step 9.

## forFeature for per-use wiring

When one shared core serves many features — one storage client, many buckets — pair `forRoot` with a `forFeature` that returns *middleware* instead of a module. It reads the root's service off the context at request time and derives the feature-scoped view, typed end to end:

```ts
import { Rhythm, decorate, derive } from "@rhythmjs/rhythm";

export const storageModule = {
  forRoot(options: StorageOptions) {
    return new Rhythm({ name: "storage" }).register(
      decorate(() => ({ storageService: createStorageService(options) })),
    );
  },
  forFeature(bucket: string) {
    return derive((ctx: { storageService: StorageService }) => ({
      bucket: ctx.storageService.bucket(bucket),
    }));
  },
};
```

```ts
// the shared client, configured once and exported
export const appStorageModule = storageModule.forRoot({ root: "./data" });

// each feature wires its own slice where it needs it
export const uploadsController = new RhythmRouter<{ storageService: StorageService }>({ name: "uploads" })
  .use(storageModule.forFeature("uploads"))
  .post("/api/uploads", multipart({ maxBytes: 10_000_000 }), async (ctx) => {
    await ctx.bucket.put(crypto.randomUUID(), ctx.form.file("file")!);
    ctx.response.status = 201;
  });

// and the feature module that owns both
export const uploadsModule = new Rhythm({ name: "uploads" })
  .register(include(appStorageModule, ({ storageService }) => ({ storageService })))
  .use(mount(uploadsController));
```

The division of labor is the convention across the ecosystem: `forRoot` owns the shared service (built once, closed on `stop()`), `forFeature` owns per-request derivation — and because it is just `derive()`, the extension is visible to the type system downstream.

## Packaging conventions

If a module outgrows the app, it publishes like any @rhythmjs package. The conventions that keep it composable:

```text
mailer/
  package.json     exports: { "./mailer": { types, default } } — one subpath
                   per module, no barrel export
  src/mailer.ts    PascalCase types (MailerOptions, MailerService),
                   lowerCamelCase instances (mailerModule, createMailerService)
  src/mailer.test.ts
```

Depend on `@rhythmjs/rhythm` as a *peer* dependency so the consumer's kernel is the only kernel, keep options serializable (they arrive at the composition root, often straight from the config service of step 7), and test the module in isolation the way step 14 tests everything else — include it into a throwaway app and assert on the context:

```ts
test("mailer sends through the console transport", async () => {
  const seen: string[] = [];
  console.log = (line: string) => void seen.push(line);

  const app = new Rhythm({ name: "test" }).register(
    include(mailerModule.forRoot({ from: "t@example.com" }), ({ mailerService }) => ({ mailerService })),
  );

  const { mailerService } = await app.callback()();
  await mailerService.send("u@example.com", "hi", "…");
  await app.stop();

  expect(seen[0]).toContain("t@example.com -> u@example.com");
});
```
