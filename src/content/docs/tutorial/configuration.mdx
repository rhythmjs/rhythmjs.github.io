## Settings as a module

Configuration is just another module. `configModule.forRoot(...factories)` runs each factory, deep-merges the results, and exposes a typed `configService`. It is async — loaders run once, when you `await` it — so the app is only built from valid settings. Register it first so everything after it can read them:

```ts
import { configModule } from "@rhythmjs/config";

const loadApp = () => ({
  port: Number(process.env.PORT ?? 3000),
});

export const appModule = new Rhythm<RhythmHttpContext>({ name: "app", type: "module" })
  .register(await configModule.forRoot(loadApp), ({ configService }) => ({ configService }))
  .use((ctx) => {
    ctx.configService.get("port"); // number — the path and value are typed
  });
```

## Namespaces with registerAs

`registerAs(token, schema, factory)` names a config namespace and validates it with any Standard Schema validator. Validation failures from *all* factories aggregate into one startup error, rejected from `await configModule.forRoot(...)` — the app refuses to boot on malformed config rather than failing later at 3 a.m.:

```ts
import { registerAs } from "@rhythmjs/config";
import { z } from "zod";

export const databaseConfig = registerAs(
  "database",
  z.object({
    url: z.url(),
    poolSize: z.coerce.number().int().min(1).default(10),
  }),
  () => ({
    url: process.env.DATABASE_URL,
    poolSize: process.env.DATABASE_POOL_SIZE,
  }),
);

export const authConfig = registerAs(
  "auth",
  z.object({ tokenTtl: z.coerce.number().default(3600) }),
  () => ({ tokenTtl: process.env.AUTH_TOKEN_TTL }),
);
```

```ts
appModule.register(
  await configModule.forRoot(loadApp, databaseConfig, authConfig),
  ({ configService }) => ({ configService }),
);

// later, anywhere on the context:
ctx.configService.get("database.url");            // string (validated URL)
ctx.configService.get("database.poolSize");       // number, defaulted
ctx.configService.getOrThrow("auth.tokenTtl");    // throws if missing
```

## Config at startup

Startup is ordinary top-level code, so wiring that needs validated settings just reads them first. Config factories are callable directly, and a failure throws before anything else is built:

```ts
// src/main.ts
const databaseSettings = await databaseConfig();
// { url: "...", poolSize: 10 } — validated or thrown

const database = await createDatabase(databaseSettings.url);
appModule.context.db = database.db;
```

<Callout title="Secrets in error messages">

Some schema libraries embed the received value in issue messages. Keep secret-bearing fields' error messages custom (`z.string().min(1, "DATABASE_URL is required")`) so a failed boot never prints the secret into logs.

</Callout>
