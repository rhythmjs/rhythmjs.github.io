Docs / Data / MikroORM

MikroORM without decorators

EntitySchema keeps entities Bun-friendly — no reflect-metadata, no decorator transforms — and the service forks a fresh EntityManager for every operation.

Install #

The PostgreSQL driver package re-exports the core; @mikro-orm/migrations adds the Migrator extension used below.

Entities without decorators #

MikroORM's decorator style needs emitDecoratorMetadata or a ts-morph discovery pass — machinery Bun's transpiler doesn't owe you. EntitySchema sidesteps all of it: the entity is a plain class, the metadata is an explicit object next to it. MikroORM hydrates rows without calling the constructor, so constructor arguments stay a convenience for creating notes.

The database provider #

MikroORM.init is async, and providers may be — the factory resolves once at setup, and orm.close() is the dispose hook. Registering the Migrator extension here means the same config serves the app and the migration runner.

Fork per operation #

MikroORM's EntityManager carries an identity map — a unit of work that must not be shared across concurrent requests. The provider holds the long-lived orm; every service method starts from orm.em.fork(), so each operation gets its own isolated context and the global-context guard never fires.

The module wiring is the shared pattern from the overview: filter(), the provider pair, the service provider (({ orm }) => …), the controller, a thrown 404.

Migrations #

Migrations are classes under src/migrations/ with up() and down() built from this.addSql(…). A short script opens the ORM, runs orm.migrator.up(), and closes it — MikroORM records applied migrations in a mikro_orm_migrations table.

Where to next #

Query-builder instead of unit-of-work: Drizzle. Generated client: Prisma. Document store: MongoDB. The full app is examples/mikro-orm-postgres.
