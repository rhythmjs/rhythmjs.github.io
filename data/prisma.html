Prisma as a provider

One PrismaClient for the app's lifetime, opened by a provider and closed by its dispose hook — with Prisma's error codes translated to plain answers at the service boundary.

Install #

The generated client is a runtime dependency; the prisma CLI is a dev tool. The schema lives in prisma/schema.prisma, and the model maps to the same notes table the other recipes use.

The database provider #

PrismaClient manages its own pool, so the provider pair is short: construct at setup, $disconnect() at teardown. Passing datasourceUrl keeps the runtime independent of the .env file the CLI reads.

Not-found at the boundary #

Prisma throws P2025 when update or delete misses. The service catches exactly that code and answers with null / false, so the controller decides the HTTP shape — it throws HttpError(404) and the filter() boundary renders it. Everything else propagates and becomes a 500.

Wiring the module #

Identical to every other recipe — only the provider name changes. The service factory receives prisma from the provider graph; the controller validates bodies with zod through validate("body", …) and checks responses with intercept(…).

Migrations #

Checked-in SQL lives under prisma/migrations/. prisma migrate deploy applies pending migrations and nothing else — it does not regenerate the client, so generation is its own step. Author new migrations with prisma migrate dev against a development database.

Where to next #

The shared pattern is introduced in the overview; the first concrete recipe is Drizzle. MikroORM adds a unit of work per request; MongoDB drops the ORM entirely. The full app is examples/prisma-postgres.
